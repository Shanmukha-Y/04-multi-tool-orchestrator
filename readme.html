Multi-Tool Orchestrator Agent

A research-concierge agent that manages a dynamic fleet of tools: they register themselves at runtime with capability tags, requests route by capability instead of hard-coded tool names, execution respects a per-session permission scope, independent tool calls run in parallel, and contradictory results from overlapping tools go through an explicit, auditable conflict-resolution policy.

01 · Why capability routing, not a tool switchboard

The difference between adding a tool and touching the orchestrator

The obvious way to build a "multi-tool agent" is a big if/elif or a hand-maintained dispatch table mapping intents to specific tool functions. It works for a demo and rots immediately: every new tool means a code change in the router, the prompt, and usually the permission logic too. It also can't express the case that actually matters in production — two tools that do the same job, so you can fail over, A/B, or cross-check them.

This orchestrator inverts that. Tools carry capability tags (weather.current, currency.convert, note.write, …) declared once in a @tool_def decorator alongside a permission scope, a priority, and a timeout. The planner LLM never emits a tool name — it decomposes the request into subtasks tagged only with capabilities, and a separate router resolves capability → whichever tools are currently registered for it, read fresh from the registry on every request. Two tools can share a capability on purpose (both weather providers do); the router either calls the higher-priority one or calls both, depending on policy.

What this buys you

Adding a ninth tool — a new weather provider, a calendar lookup, anything — is one decorator and zero changes to planner.py, router.py, or the graph. The planner's prompt is generated from registry.capability_catalog() at call time, so a tool registered five seconds ago is something the very next planning call can route to. Milestone 5's demo proves this by registering a third weather provider mid-process and re-running the same request.

03 · Permission scoping as a planner input, not a runtime crash

Denials are structured data the planner adapts to

Every tool declares one ScopeClass: read (querying data, no side effects — weather, currency, calculator, file reads), network (an external, less-trusted call — web search), or write (a real side effect — writing a note, sending an email). A session grants a subset, e.g. --scope read,network.

The permission gate doesn't reject a request outright when a scope is missing. It produces a structured Denial — which tool, which capability, which scope was required — for every candidate it drops. If a subtask is left with zero runnable candidates, the graph routes back to the planner exactly once, with those denials appended to its prompt: "these capabilities are unavailable this session, drop what needs them and say what you couldn't do." The bound to one replan matters as much as the replan itself — a 9B model given an open-ended retry loop will sometimes retry the same denied capability forever; capping it means the worst case is one wasted planning call, not a hang.

A capability the router can't find any tool for at all (the model hallucinated a capability outside the catalog) is handled differently — as an honest failure recorded in the execution report, not a replan trigger, since retrying rarely fixes a hallucination and a bounded retry budget is better spent on real denials.

04 · Parallel execution and conflict resolution

Real concurrency, proven with timestamps — and an explicit policy when tools disagree

Subtasks form a dependency DAG via an optional depends_on list (a note that summarizes results depends on the subtasks that produced them; independent lookups don't depend on anything). The executor topologically sorts subtasks into batches and runs every call in a batch concurrently with asyncio.gather; each call is individually wrapped in its own try/except and asyncio.wait_for, so one tool's timeout or bug produces a failed ToolResult for that call alone — it never takes its batch mates down. tests/test_executor.py proves this two ways: fake tools record their own start/finish timestamps and the test asserts real overlap (not just that asyncio.gather was called), and a separate test injects a raising tool into a batch and asserts its neighbor still succeeds.

The router can deliberately call every candidate for a capability (--router-mode all, the default) rather than just the top-priority one — that redundancy is what surfaces genuine disagreement between tools, which the resolver then has to adjudicate under one of three policies:

priority
Picks the result from whichever tool has the higher configured priority in its manifest. Deterministic, free, no model call — the right default when one provider is simply known to be more trustworthy.
freshest
Picks the result whose payload carries the most recent observed_at timestamp. The two built-in weather mocks are deliberately tuned so priority and freshest disagree (the higher-priority provider is also the stalest one) — a realistic tradeoff, not a toy example.
llm_adjudicate
Sends both candidate results to qwen3.5:9b and asks it to pick one and explain why, in JSON mode with a one-shot repair retry. If the model names a tool that wasn't actually a candidate (small models occasionally do this), the resolver rejects the hallucination and falls back to the first candidate rather than propagating it; if the call fails outright, it falls back the same way and says so plainly. The rationale is carried into the execution report either way, so a reviewer can see why the agent trusted one number over another.

Every run prints a batch-by-batch wall-time report — actual wall time next to a summed per-call estimate of what running the same batch sequentially would have cost — and orc run --sequential re-runs the same request with each batch executed one call at a time, for an honest, actually-measured baseline rather than an estimate.

05 · Install & run

# from the project root, with a local Ollama server already running $ ollama pull qwen3.5:9b # if not already pulled $ uv sync $ uv run pytest # 40 tests, ~1s, no network $ uv run pytest -m integration # 2 live end-to-end requests, several minutes $ uv run orc tools # live registry: capabilities, scopes, priorities $ uv run orc run "Compare the weather in Tokyo and Paris, convert 100 USD to JPY, save a note" $ uv run orc run "…" --scope read --resolve-policy llm_adjudicate $ uv run orc run "…" --sequential # wall-time baseline, no parallel batching $ uv run orc demo # the full walkthrough below, one command

The model name lives in exactly one place, config.py, overridable via ORCHESTRATOR_MODEL for anyone running a different local model.

06 · Demo walkthrough

orc demo runs all five steps below, end to end, in one process

StepWhat it shows
1orc tools — the live registry: 8 tools, their capabilities, scopes, and priorities.
2A multi-part request (weather × 2 cities, currency conversion, a summary note) under full scope — the execution report shows the subtask plan, the parallel batches, and wall-time saved vs. a sequential estimate.
3The identical request under --scope read, plus a second, single-purpose write request ("send an email confirming the trip") under the same restricted scope — a small local planner doesn't always keep an optional write-scoped subtask (the note) in a compound plan, so the dedicated request is what reliably shows the denial → bounded replan → "here's what I couldn't do" path end to end.
4A weather-only request run three times, once per resolution policy — priority and freshest disagree with each other by design, and llm_adjudicate prints the model's own rationale for its pick.
5The money shot. A third weather provider, weather_c, is registered mid-session — after the registry has already been queried several times in this same process — and the very next run routes to it immediately. No restart, no cache invalidation, no code path touched outside the one call to registry.register().

Honest limitation

qwen3.5:9b is a small model asked to do structured multi-step planning. On a compound request it will sometimes decide a "nice to have" subtask (the note) isn't worth including, independent of scope — that's a planning-quality ceiling, not an orchestrator bug, and it's why the permission-denial demo pairs the compound request with one that has only a single, unavoidably write-scoped path.

Step 5 is the actual claim of the "dynamic fleet of tools" framing made concrete: the registry is queried live on every planning call (registry.capability_catalog() inside planner.build_system_prompt) and every routing call (registry.find_by_capability inside router.route) — there is no snapshot anywhere for a newly-registered tool to be stale against.
